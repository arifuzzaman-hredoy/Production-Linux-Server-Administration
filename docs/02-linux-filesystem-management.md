## 1. Overview

Linux filesystem management is one of the fundamental responsibilities of a Linux System Administrator and DevOps Engineer.

A Linux administrator must understand how files and directories are organized, how to search and manage files, how permissions work, how storage is consumed, and how to investigate filesystem-related problems.

In production environments, incorrect filesystem operations can cause application downtime, data loss, configuration failures, and service interruptions.

This stage focuses on practical filesystem administration using Ubuntu Linux.

### Learning Objectives

After completing this stage, the learner should be able to:

- Understand the Linux filesystem hierarchy.
- Navigate using absolute and relative paths.
- Create, copy, move, rename, and remove files and directories.
- Search for files using `find` and `locate`.
- Search file contents using `grep`.
- Understand inodes and filesystem links.
- Differentiate hard links and symbolic links.
- Investigate disk space and inode consumption.
- Use `df`, `du`, `lsblk`, and `findmnt`.
- Create configuration backups.
- Compare configuration changes.
- Perform safe configuration rollback.
- Troubleshoot broken symbolic links and permission problems.
- Investigate production storage issues without damaging running services.

## 2. Linux Filesystem Hierarchy

Linux uses a hierarchical filesystem structure that starts from the root directory `/`.

Unlike Windows, Linux does not use separate drive letters such as `C:` or `D:` as the primary filesystem navigation model.

All files and directories are organized under `/`.

### 2.1 Important Linux Directories

| Directory | Purpose |
|---|---|
| `/` | Root of the entire filesystem hierarchy |
| `/bin` | Essential user commands; commonly linked to `/usr/bin` |
| `/sbin` | Essential system administration commands; commonly linked to `/usr/sbin` |
| `/boot` | Kernel and bootloader-related files |
| `/dev` | Device files |
| `/etc` | System-wide configuration files |
| `/home` | Regular users' home directories |
| `/root` | Root user's home directory |
| `/lib` | Essential shared libraries; commonly linked to `/usr/lib` |
| `/media` | Mount points for removable media |
| `/mnt` | Temporary mount points |
| `/opt` | Optional third-party application software |
| `/proc` | Virtual filesystem containing process and kernel information |
| `/run` | Runtime system data |
| `/srv` | Data served by system services |
| `/sys` | Virtual filesystem exposing kernel and device information |
| `/tmp` | Temporary files |
| `/usr` | User-space programs, libraries, and shared resources |
| `/var` | Variable data such as logs, caches, and application state |

### 2.2 Important Directory Examples

**`/etc` — Configuration**

Examples:

```bash
/etc/hostname
/etc/hosts
/etc/fstab
/etc/ssh/
/etc/nginx/
```

**`/var` — Variable Data**

Examples:

```bash
/var/log/
/var/cache/
/var/lib/
/var/tmp/
```

**`/home` — User Data**

Example:

```bash
/home/ubuntu/
```

**`/proc` — Process and Kernel Information**

Examples:

```bash
/proc/cpuinfo
/proc/meminfo
/proc/loadavg
/proc/mounts
```

`/proc` is a virtual filesystem. Its contents are generated by the kernel and do not behave like ordinary files stored on disk.

### 2.3 Inspect the Filesystem Hierarchy

List the root directory:

```bash
ls /
```

Show detailed information:

```bash
ls -lah /
```

Inspect important directories:

```bash
ls -ld /etc /var /home /root /usr /tmp /dev /proc /sys /run
```

Display directory structure:

```bash
tree -L 2 /
```

Note: `tree` may need to be installed first.

```bash
sudo apt install tree
```

Check filesystem mount points:

```bash
findmnt
```

Display filesystem types and disk usage:

```bash
df -hT
```

## 3. Absolute and Relative Paths

A path identifies the location of a file or directory.

Linux supports two major path types.

### 3.1 Absolute Path

An absolute path starts from the root directory `/`.

Examples:

```bash
/etc/hostname
/var/log/syslog
/home/ubuntu/
```

Absolute paths identify a location independently of the current working directory.

### 3.2 Relative Path

A relative path is interpreted from the current working directory.

Examples:

```bash
var/log
../
./config/app.conf
```

### 3.3 Special Path Symbols

| Symbol | Meaning |
|---|---|
| `/` | Root directory |
| `.` | Current directory |
| `..` | Parent directory |
| `~` | Current user's home directory |
| `-` | Previous working directory when used with `cd -` |

### 3.4 Navigation Commands

Show the current directory:

```bash
pwd
```

Show the current user's home directory:

```bash
echo "$HOME"
```

Navigate to the root directory:

```bash
cd /
```

Navigate to `/var/log`:

```bash
cd /var/log
```

Navigate to the parent directory:

```bash
cd ..
```

Navigate to the home directory:

```bash
cd ~
```

Return to the previous directory:

```bash
cd -
```

### Practical Example

```bash
cd /var/log
pwd

cd ..
pwd

cd ~
pwd
```

## 4. File and Directory Management

Linux provides several commands for creating, copying, moving, renaming, and deleting files and directories.

### 4.1 Create Directories

Create a directory:

```bash
mkdir my-directory
```

Create nested directories:

```bash
mkdir -p project/config/nginx
```

The `-p` option creates parent directories when required and does not report an error if the directory already exists.

### 4.2 Create Files

Create an empty file:

```bash
touch app.log
```

Create multiple files:

```bash
touch app.log error.log access.log
```

### 4.3 List Files

Basic listing:

```bash
ls
```

Detailed listing:

```bash
ls -l
```

Show hidden files:

```bash
ls -a
```

Human-readable detailed listing:

```bash
ls -lah
```

Display permissions, ownership, sizes, and timestamps:

```bash
ls -lah
```

### 4.4 Copy Files

Copy a file:

```bash
cp source.txt destination.txt
```

Copy into a directory:

```bash
cp app.conf backups/
```

Preserve file attributes:

```bash
cp -p app.conf backups/
```

Copy a directory recursively:

```bash
cp -r source-directory/ destination-directory/
```

Preserve attributes recursively:

```bash
cp -a source-directory/ destination-directory/
```

`cp -a` is useful for backups because it preserves many file attributes, including permissions, timestamps, and symbolic links.

### 4.5 Move and Rename Files

Move a file:

```bash
mv app.log logs/
```

Rename a file:

```bash
mv old-name.conf new-name.conf
```

Move a directory:

```bash
mv old-directory/ new-directory/
```

### 4.6 Delete Files and Directories

Delete a file:

```bash
rm app.log
```

Delete an empty directory:

```bash
rmdir empty-directory
```

Delete a directory recursively:

```bash
rm -r directory/
```

Force deletion:

```bash
rm -f app.log
```

Recursive forced deletion:

```bash
rm -rf directory/
```

**Production warning:**

`rm -rf` can permanently remove large amounts of data.

Never execute destructive commands on production paths without verifying the target.

Avoid careless commands such as:

```bash
sudo rm -rf /var/lib/docker
sudo rm -rf /etc
sudo rm -rf /
```

These can destroy application data, system configuration, or the operating environment.

Always inspect the target path before deletion.

### 4.7 Write and Append File Content

Overwrite file content:

```bash
echo "APP_NAME=TaskFlow" > app.conf
```

Append content:

```bash
echo "APP_PORT=8080" >> app.conf
```

Important difference:

| Operator | Behavior |
|---|---|
| `>` | Creates or overwrites a file |
| `>>` | Creates a file if needed or appends content |

Inspect file content:

```bash
cat app.conf
```

Read a file page by page:

```bash
less app.conf
```

Display the first 10 lines:

```bash
head app.conf
```

Display the last 10 lines:

```bash
tail app.conf
```

Follow new log entries:

```bash
tail -f app.log
```

### 4.8 Inspect File Information

Identify a file type:

```bash
file app.conf
```

Display detailed metadata:

```bash
stat app.conf
```

Show inode numbers:

```bash
ls -i app.conf
```

## 5. File Search and Content Search

Linux administrators frequently need to locate files and search application logs.

Three important tools are:

- `find`
- `locate`
- `grep`

### 5.1 The `find` Command

General syntax:

```bash
find [path] [conditions] [actions]
```

Find files in the current directory:

```bash
find . -type f
```

Find directories:

```bash
find . -type d
```

Find a specific filename:

```bash
find /home/ubuntu -name "app.conf"
```

Case-insensitive search:

```bash
find /home/ubuntu -iname "APP.CONF"
```

Find all `.log` files:

```bash
find /var/log -type f -name "*.log"
```

Find files larger than 100 MB:

```bash
find /var -type f -size +100M
```

Find empty files:

```bash
find . -type f -empty
```

Find files modified within the last 24 hours:

```bash
find . -type f -mtime -1
```

Find files modified within the last 60 minutes:

```bash
find . -type f -mmin -60
```

Find files owned by a user:

```bash
find /home -user ubuntu
```

Find files with a specific permission mode:

```bash
find . -type f -perm 600
```

Find files with at least the specified permission bits:

```bash
find . -type f -perm -644
```

Find files with any of the specified permission bits:

```bash
find . -type f -perm /111
```

### 5.2 The `locate` Command

`locate` searches a database of file paths instead of scanning the filesystem every time.

Install `plocate`:

```bash
sudo apt update
sudo apt install plocate
```

Update its database:

```bash
sudo updatedb
```

Search for a file:

```bash
locate app.conf
```

Search by filename pattern:

```bash
locate "*.tf"
```

Check the version:

```bash
locate --version
```

**Important:** `locate` can return outdated results if its database has not been updated.

Use:

```bash
sudo updatedb
```

when you need a refreshed index.

### 5.3 The `grep` Command

`grep` searches for text patterns inside files.

General syntax:

```bash
grep [options] "pattern" filename
```

Search for a word:

```bash
grep "ERROR" app.log
```

Case-insensitive search:

```bash
grep -i "error" app.log
```

Show matching line numbers:

```bash
grep -n "ERROR" app.log
```

Search recursively:

```bash
grep -r "ERROR" /var/log/
```

Invert the match:

```bash
grep -v "INFO" app.log
```

Count matching lines:

```bash
grep -c "ERROR" app.log
```

Combine options:

```bash
grep -in "error" app.log
```

**Production example:**

Search application logs for errors:

```bash
grep -in "error" /var/log/syslog
```

Be careful when sharing log output because logs can contain IP addresses, usernames, tokens, and other sensitive information.

## 6. Inodes, Hard Links, and Symbolic Links

### 6.1 What Is an Inode?

An inode is a filesystem data structure that stores metadata about a file.

An inode contains information such as:

- File type
- File permissions
- Owner ID
- Group ID
- File size
- Timestamps
- Disk block references
- Link count

An inode does not normally store the filename itself.

Directory entries map filenames to inode numbers.

### 6.2 Inspect Inodes

Display inode numbers:

```bash
ls -i app.conf
```

Display detailed inode metadata:

```bash
stat app.conf
```

Show filesystem inode usage:

```bash
df -i
```

### 6.3 What Is a Hard Link?

A hard link is another directory entry pointing to the same inode as an existing file.

Create a hard link:

```bash
ln app.conf app.conf.hardlink
```

Compare inode numbers:

```bash
ls -li app.conf app.conf.hardlink
```

Both files should show the same inode number.

Check the link count:

```bash
stat app.conf
```

The link count increases when another hard link is created.

**Important properties:**

- Hard links share the same inode.
- Changes to the underlying file data are visible through both names.
- Removing one filename does not remove the data while another hard link remains.
- Hard links normally cannot cross filesystem boundaries.
- Creating hard links to directories is generally prohibited for regular users.

### 6.4 What Is a Symbolic Link?

A symbolic link, also called a symlink, is a special file that stores a path to another file or directory.

Create a symbolic link:

```bash
ln -s app.conf app.conf.symlink
```

Inspect it:

```bash
ls -l app.conf.symlink
```

Display the link target:

```bash
readlink app.conf.symlink
```

Resolve the full path:

```bash
readlink -f app.conf.symlink
```

### 6.5 Hard Link vs Symbolic Link

| Feature | Hard Link | Symbolic Link |
|---|---|---|
| Inode | Same inode as target | Separate inode |
| Target dependency | Does not depend on the original filename | Depends on target path |
| Cross-filesystem | No | Yes, if target path is accessible |
| Directory linking | Normally prohibited | Supported |
| Broken link | Not caused by renaming another hard-link name | Can become broken if target disappears |
| Storage | Another directory entry | Separate link file containing a path |

### 6.6 Directory Symbolic Links

Create a directory symlink:

```bash
ln -s /home/ubuntu/linux-filesystem-lab/logs logs-link
```

Inspect:

```bash
ls -l logs-link
```

Access the linked directory:

```bash
ls logs-link/
```

### 6.7 Broken Symbolic Links

A symbolic link becomes broken when its target cannot be resolved.

Check the target:

```bash
readlink broken-link
```

Resolve it:

```bash
readlink -f broken-link
```

Find broken symbolic links:

```bash
find -L . -type l
```

Check whether a path is a broken symbolic link:

```bash
if [ -L broken-link ] && [ ! -e broken-link ]; then
    echo "Broken symbolic link"
fi
```

## 7. Disk Usage Investigation

Disk monitoring is an important responsibility in production Linux administration.

A full filesystem can prevent applications from writing logs, creating temporary files, updating databases, or starting services.

Two different resource limits must be monitored:

1. Disk space
2. Inode availability

### 7.1 The `df` Command

`df` reports filesystem-level disk space usage.

Show filesystem usage:

```bash
df
```

Human-readable output:

```bash
df -h
```

Display filesystem types:

```bash
df -hT
```

Check inode usage:

```bash
df -i
```

Check a specific path:

```bash
df -h /
```

**Interpretation:**

| Column | Meaning |
|---|---|
| Filesystem | Filesystem or device |
| Size | Total capacity |
| Used | Used space |
| Avail | Available space |
| Use% | Percentage used |
| Mounted on | Mount point |

### 7.2 The `du` Command

`du` reports disk usage for files and directories.

Show directory size:

```bash
du -sh /var
```

Show subdirectory sizes:

```bash
du -h --max-depth=1 /var
```

Show all files and directories:

```bash
du -ah /var
```

Sort largest entries first:

```bash
du -ah /var | sort -hr
```

Stay within the same filesystem:

```bash
du -xhd1 /
```

Check a specific directory:

```bash
du -sh /var/log
```

### 7.3 `df` vs `du`

| Feature | `df` | `du` |
|---|---|---|
| Purpose | Filesystem usage | File and directory usage |
| Scope | Mounted filesystem | Selected paths |
| Shows available filesystem space | Yes | No |
| Finds large directories | No | Yes |
| Useful for | Overall disk monitoring | Storage investigation |

### 7.4 Understanding `sort`

Human-readable sorting:

```bash
sort -h
```

Reverse human-readable sorting:

```bash
sort -hr
```

`sort -r` alone reverses lexical ordering; it does not understand human-readable sizes such as `1G` and `500M`.

### 7.5 Inspect Block Devices

List block devices:

```bash
lsblk
```

Show filesystem types:

```bash
lsblk -f
```

Display mounted filesystems:

```bash
findmnt
```

Inspect a specific path's mount:

```bash
findmnt -T /
```

### 7.6 Understand Docker and OverlayFS Storage

Production Docker environments can contain multiple storage layers.

Useful read-only commands:

```bash
docker system df
```

Detailed Docker disk usage:

```bash
docker system df -v
```

List containers:

```bash
docker ps -a
```

List images:

```bash
docker images
```

List volumes:

```bash
docker volume ls
```

Inspect Docker storage directories:

```bash
sudo du -h --max-depth=1 /var/lib/docker
```

Inspect containerd storage:

```bash
sudo du -h --max-depth=1 /var/lib/containerd
```

Inspect OverlayFS mounts:

```bash
findmnt -t overlay
```

Important OverlayFS concepts:

- `lowerdir`: Read-only image or filesystem layers.
- `upperdir`: Writable layer.
- `workdir`: Internal working directory used by OverlayFS.

A mounted OverlayFS view can make directory size calculations confusing.

For example:

```bash
sudo du -hd1 /var/lib/docker
```

and:

```bash
sudo du -xhd1 /var/lib/docker
```

may report different totals because `-x` does not cross into other filesystems.

**Production safety:**

Never delete Docker or containerd storage directories manually.

Do not casually run:

```bash
docker system prune
docker volume prune
```

These operations can remove resources needed by running or future workloads.

Always investigate usage and dependencies before considering cleanup.

## 8. Production File Management

Production configuration files should be handled carefully.

Before changing a configuration:

1. Identify the correct file.
2. Inspect its current contents and permissions.
3. Create a backup.
4. Prepare the new configuration.
5. Compare old and new versions.
6. Apply the change.
7. Validate the application configuration.
8. Monitor the service.
9. Roll back if necessary.

### 8.1 Create a Timestamped Backup

Create a backup directory:

```bash
mkdir -p backups
```

Generate a timestamp:

```bash
date +%Y%m%d-%H%M%S
```

Create a backup filename:

```bash
BACKUP_FILE="backups/app.conf.$(date +%Y%m%d-%H%M%S).bak"
```

Copy the configuration while preserving metadata:

```bash
cp -p config/app.conf "$BACKUP_FILE"
```

Verify the backup:

```bash
ls -lah backups/
```

Compare the files:

```bash
cmp config/app.conf "$BACKUP_FILE"
```

If both files are identical, `cmp` exits with status code `0` and prints no difference.

Check the exit status:

```bash
echo $?
```

### 8.2 Inspect File Metadata

```bash
stat config/app.conf
```

Check file permissions:

```bash
ls -l config/app.conf
```

Compare checksums:

```bash
sha256sum config/app.conf "$BACKUP_FILE"
```

Matching SHA-256 checksums indicate that the file contents match.

### 8.3 Safely Modify a Configuration

Create a temporary configuration file:

```bash
cp -p config/app.conf config/app.conf.tmp
nano config/app.conf.tmp
```

Example:

```ini
APP_NAME=TaskFlow
APP_PORT=8081
APP_ENV=production
```

Compare the old and new versions:

```bash
diff -u config/app.conf config/app.conf.tmp
```

If the change is correct, replace the original:

```bash
mv config/app.conf.tmp config/app.conf
```

When both files are on the same filesystem, renaming a temporary file over the destination is normally an atomic replacement.

**Important:** Atomic replacement does not automatically preserve the original file's ownership, permissions, ACLs, or other metadata. Set and verify the required metadata before deploying a production configuration.

### 8.4 Verify the Updated Configuration

```bash
cat config/app.conf
```

Inspect metadata:

```bash
stat config/app.conf
```

Compare the checksum:

```bash
sha256sum config/app.conf
```

### 8.5 Roll Back a Configuration

Restore from a backup:

```bash
cp -p "$BACKUP_FILE" config/app.conf.restore
mv config/app.conf.restore config/app.conf
```

Verify:

```bash
cmp config/app.conf "$BACKUP_FILE"
```

Check the checksum:

```bash
sha256sum config/app.conf "$BACKUP_FILE"
```

A successful rollback restores the expected file content.

### 8.6 Production Service Validation

For an Nginx configuration change:

```bash
sudo nginx -t
```

If the configuration test succeeds:

```bash
sudo systemctl reload nginx
```

Check service status:

```bash
sudo systemctl status nginx
```

Do not reload or restart a production service until its configuration has been validated.

## 9. Filesystem Troubleshooting

### 9.1 Identify a File Type

```bash
file app.conf
```

This helps determine whether a file is plain text, binary, an archive, or another type.

### 9.2 Inspect Detailed Metadata

```bash
stat app.conf
```

Useful information includes:

- File size
- Inode
- Permissions
- Ownership
- Link count
- Timestamps

### 9.3 Investigate a Path

```bash
namei -l /home/ubuntu/project/config/app.conf
```

`namei -l` displays every component of a path and its permissions.

This is particularly useful when a user receives `Permission denied`.

### 9.4 Resolve Symbolic Links

```bash
readlink app-config-link
```

```bash
readlink -f app-config-link
```

```bash
realpath app-config-link
```

### 9.5 Check Broken Links

```bash
find -L . -type l
```

Check one link:

```bash
if [ -L app-config-link ] && [ ! -e app-config-link ]; then
    echo "Broken symbolic link"
else
    echo "Link is valid or path is not a symbolic link"
fi
```

### 9.6 Investigate Permission Problems

Check the current user:

```bash
whoami
```

Check group membership:

```bash
id
```

Inspect permissions:

```bash
ls -l app.conf
```

Inspect every parent directory:

```bash
namei -l /home/ubuntu/project/config/app.conf
```

If ACLs are installed:

```bash
getfacl app.conf
```

A user needs appropriate permissions on the file and execute (`x`) permissions on each parent directory to access a file through its path.

### 9.7 Investigate Disk Space Problems

Start with:

```bash
df -h
df -i
```

Find large directories:

```bash
sudo du -xhd1 /var
```

Investigate large files:

```bash
sudo find /var -xdev -type f -size +500M -ls
```

Check deleted files still held open by processes:

```bash
sudo lsof +L1
```

Inspect mount points:

```bash
findmnt
```

A deleted file can continue consuming disk space while a process still holds it open.

### 9.8 Important Troubleshooting Concepts

**Disk space full:**

The filesystem has insufficient available blocks.

**Inode exhaustion:**

The filesystem has run out of available inodes, even if some disk space remains.

**Permission denied:**

The current user may lack file permissions, directory traversal permissions, or required ACL access.

**Broken symbolic link:**

The link's stored target path cannot be resolved.

**Unexpected disk usage:**

Investigate mounted filesystems, open deleted files, container storage, and large directories before taking action.

## 10. Production Troubleshooting Scenarios

### Scenario 1 — Root Filesystem Is 95% Full

Initial investigation:

```bash
df -h /
df -i /
```

Identify large directories:

```bash
sudo du -xhd1 /
```

Investigate `/var`:

```bash
sudo du -xhd1 /var
```

Find large files:

```bash
sudo find /var -xdev -type f -size +500M -ls
```

Check deleted open files:

```bash
sudo lsof +L1
```

Check Docker storage:

```bash
docker system df -v
```

Do not delete data until its purpose and ownership are understood.

### Scenario 2 — Application Cannot Read Its Configuration

Investigate:

```bash
whoami
id
ls -l /path/to/app.conf
namei -l /path/to/app.conf
```

Check ACLs if available:

```bash
getfacl /path/to/app.conf
```

Identify the exact permission or ownership problem before changing anything.

### Scenario 3 — Symbolic Link Is Broken

Inspect:

```bash
ls -l mylink
readlink mylink
readlink -f mylink
```

Check:

```bash
test -L mylink
test -e mylink
```

If the link exists but its target does not, investigate whether the target was moved, renamed, or deleted.

### Scenario 4 — Configuration Change Causes an Application Failure

Actions:

1. Check application logs.
2. Validate the configuration.
3. Inspect the changed file.
4. Restore the known-good backup if required.
5. Validate the restored configuration.
6. Reload the service safely.
7. Verify application health.

For Nginx:

```bash
sudo nginx -t
sudo systemctl status nginx
```

## 12. Production Best Practices

1. Always verify the current directory before performing file operations.
2. Use absolute paths in administrative scripts when practical.
3. Inspect file permissions and ownership before modifying production files.
4. Back up configuration files before changing them.
5. Use temporary files and compare changes before applying them.
6. Validate application configurations before reloading services.
7. Monitor both disk-space and inode usage.
8. Investigate large directories before deleting anything.
9. Understand mount points and filesystem boundaries.
10. Never manually delete active Docker or containerd storage.
11. Avoid exposing sensitive log contents in public reports.
12. Do not store credentials or environment secrets in Git repositories.
13. Verify every important operation.
14. Maintain a tested rollback procedure for production changes.
